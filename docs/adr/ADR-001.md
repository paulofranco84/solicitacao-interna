# ADR-001 — Persistência relacional e execução local da API de solicitações

**Squad:** Polaris

**Status:** Implementada localmente; publicação e CI do incremento pendentes

**Última atualização:** 2026-11-13

## Contexto

A decisão original foi usar um banco relacional no projeto. A API do Hack
precisa cadastrar solicitações internas, persistir os dados e permitir que o
time execute e verifique o fluxo no próprio PC, sem instalar um servidor de banco.

Esta atualização detalha a implementação existente e registra o incremento
realizado em 13/11/2026: health check, smoke local, teste do health e documentação.
Não representa implantação em produção ou validação em todos os PCs do time.

## Decisão e justificativa

Usar **SQLite com Entity Framework Core**, em uma API **ASP.NET Core .NET 8**.
O SQLite mantém a persistência relacional escolhida originalmente, com um
arquivo local e sem dependência de um servidor externo para a demonstração.

Manter o fluxo em camadas:

```text
Cliente HTTP → SolicitacoesController
             → ISolicitacaoService / SolicitacaoService
             → SolicitacoesDbContext / EF Core → SQLite
```

O controller valida a entrada e mapeia a resposta. O serviço cria a entidade
e persiste os dados de forma assíncrona, propagando o `CancellationToken`.
As respostas usam DTOs, sem expor a entidade de persistência.
Não há integração HTTP externa nem cache nesta implementação.

## Contrato dos endpoints

| Método e rota | Entrada | Resultado |
| --- | --- | --- |
| `POST /solicitacoes` | JSON com `descricao` e `categoria` | `201 Created` com `{"id": <inteiro positivo>}` |
| `GET /health` | Sem corpo | `200 OK`, `text/plain`, corpo `Healthy` |

### Criação de solicitação

- `descricao` e `categoria` são strings obrigatórias.
- Valores ausentes, `null`, vazios ou somente espaços em branco são rejeitados.
- A validação retorna `400` com `ValidationProblemDetails` e erros por campo,
  sem criar registro.
- O identificador é um inteiro de 64 bits gerado pelo banco.
- Não há catálogo fechado de categorias, limite de tamanho definido pela
  aplicação ou remoção de espaços dos valores aceitos.
- Cada POST válido cria um novo registro; não há deduplicação ou idempotência.
- Não há rota de consulta por identificador nem cabeçalho `Location` no `201`.

Erros de model binding são tratados pelo ASP.NET Core. Falhas de infraestrutura
não possuem contrato de erro customizado nesta versão.

### Health check

Adicionar `AddHealthChecks()` e mapear `/health` com `MapHealthChecks`, usando
o suporte nativo do ASP.NET Core, sem dependência adicional.

O endpoint é **liveness**, sem checks do SQLite. Ele demonstra que a API está
em execução, mas não garante disponibilidade de gravação. Por isso, a
verificação local inclui também o POST com dados fictícios.

## Persistência e configuração

- Banco padrão: `API_Solicitacoes/solicitacoes.db`.
- Conexão: `ConnectionStrings:Solicitacoes`, com `Data Source=solicitacoes.db`.
- Sobrescrita por ambiente: `ConnectionStrings__Solicitacoes`.
- Caminhos relativos são resolvidos a partir da raiz do projeto da API.
- `EnsureCreatedAsync` cria o banco e a tabela na inicialização.
- A tabela `solicitacoes` contém `id` (chave primária gerada), `descricao` e
  `categoria` (obrigatórios).
- O arquivo permanece entre reinicializações. Não há migrations ou estratégia
  de evolução de schema implementadas.

O perfil `http` usa `http://localhost:5245` e o ambiente `Development`.
Swagger UI e seu JSON são disponibilizados somente em `Development`.
Os comandos completos de build, teste e `dotnet run` estão no
[README](../../README.md).

## Consequências e limites

- A execução local não requer servidor de banco, mas depende do SDK/runtime,
  das dependências NuGet e de acesso de escrita ao arquivo SQLite.
- O smoke válido grava dados; usar somente payloads fictícios e banco de teste.
- O health não substitui uma verificação de persistência.
- Alterações futuras de schema exigem uma estratégia além de `EnsureCreatedAsync`.
- As rotas atuais não possuem autenticação implementada; esta ADR documenta
  o escopo do Hack, não prontidão para produção.
- O OpenAPI estático e o Swagger gerado precisam ser mantidos consistentes.
- Não foram implementadas novas operações CRUD além da criação.
